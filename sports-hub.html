Sports Hub

A self-hosted data pipeline and dashboard for the teams I follow: the Indiana Pacers, Purdue Boilermakers, Indianapolis Colts, and Detroit Red Wings. Python pulls data from three sports APIs into PostgreSQL, and it all runs 24/7 on a home server.

The why

Why I built it

Learn by building

I came into data engineering strong on concepts and visualization but light on hands-on Python and SQL. A real project with messy APIs and a real database teaches more than tutorials do, so the goal was to learn the craft, not just ship an app.

One place for my teams

My four teams span four leagues and four different corners of ESPN. I wanted rosters, scores, and stats together in one dashboard built the way I'd want to read it.

Deeper than the box score

It's built for a small group of friends and family. The goal is more charts, trends, and context than the major sports apps give you.

Keep it free

Free APIs, open-source tools, and hardware I already own. It's a constraint I set on purpose, and it forced some useful engineering decisions about what's worth building.

The how

How it works

A classic extract → load → serve pipeline, sized for a single home server.

1 · Extract

Python scripts call the ESPN, balldontlie, and NHL APIs. A reusable helper, extract_espn_fields(), normalizes ESPN's nested JSON so every sport comes out in the same shape.

2 · Load

db.py writes to PostgreSQL through psycopg2 with parameterized queries and ON CONFLICT … DO UPDATE upserts. The pipeline can re-run safely without creating duplicates.

3 · Serve

Postgres and the dashboard run on a home Linux server, reachable over Tailscale's encrypted network with HTTPS and no ports open on my router. Development happens on my Mac against a local Postgres copy.

Engineering decisions

The choices that mattered

Long-format stats table

Basketball, football, and hockey track completely different stats. Instead of a wide table full of empty columns, stats are stored one row per player, per game, per stat. Adding a new sport doesn't change the schema at all.

Shared tables, not per-team tables

One teams table and one players table filtered by team_id, instead of a table per team. That means less to maintain, and cross-team queries become one simple SELECT.

Stable external IDs

Upserts match on (league, external_id). When I moved the database to the server, I found a duplicate Colts row caused by mixing two ID sources. Lesson: never swap an ID source mid-project, or matches silently fail and duplicates pile up.

Consolidate on one API where possible

Digging into ESPN's hockey endpoint showed it had richer data than expected (handedness, structured injury info). Using ESPN across sports cut down the number of API formats the code has to handle.

Hardcode when the source has gaps

ESPN returns no venue data for college basketball, so Purdue's arena and city, plus each team's founding year, are hardcoded. It's a deliberate trade-off: a few static values beat a brittle workaround.

Secure, headless deployment

The server pulls code from GitHub with a read-only SSH deploy key. Secrets live in a .env file that never touches Git, and psycopg2-binary avoids compile failures on ARM hardware.

Takeaways

What I learned

  • Trust the database, not the docs. I verify state with SQL queries instead of assuming my notes are current.
  • Unofficial APIs are best-effort. ESPN and NHL endpoints are undocumented and can change without warning, so the extract layer is kept isolated and easy to patch.
  • Hardware constraints shape design. A small home server means efficient queries and nightly batch loads instead of live polling.
  • Documentation is part of the product. A living SCHEMA.md and project notes file keep the project understandable weeks later.
